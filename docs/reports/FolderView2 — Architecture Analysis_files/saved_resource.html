It owns no container state, reimplements no behaviour, and inherits everything the host page already does. That single decision explains almost every structural quirk in the codebase.

01 — The problem it is solving

No extension point, so make one

Unraid’s Docker tab is rendered by dynamix.docker.manager, a first-party page a plugin cannot modify. It emits a flat table of container rows and that is the end of its contract. A homelab with forty containers is an unreadable wall, and Unraid ships no grouping primitive. Three ways in existed:

ApproachCostVerdict
Fork the Docker tabRe-fork on every Unraid release.Fatal
Re-render the list from the Docker APIReimplement every row behaviour Unraid attaches — context menus, log links, update checks, autostart switches, live-stat wiring — and keep them in sync forever.Enormous
Let Unraid render, then rearrange the DOMFragile against internal changes.Chosen

A container inside a folder is the same DOM node Unraid created, moved. Not a copy. Its start/stop menu, update indicator and autostart toggle keep working with zero plugin code.

The trade is honest and, two years on, vindicated: the changelog is a long list of “fix for Unraid v7” entries — the recurring cost of monkey-patching — but a re-render approach would have had to own the whole surface instead, and would have died at 6.10.

03 — The core mechanism

Intercept, reconcile, relocate

The plugin must run after Unraid draws its table but before the user sees it. No such event exists, so it wraps the functions that do the drawing — window.loadlist and window.listview on Docker, and an $.ajaxPrefilter on the Dashboard and VM tabs, which have no equivalent global to patch.

One refresh, start to finish

01

Patched loadlist fires four XHRs — and does not await themfolders · saved order · container info · live order. The network round-trips overlap Unraid’s own render entirely.

02

loadlist_original() → Unraid renders its rowsFull stock behaviour, untouched.

03

Patched listview() runs after the originalRows are now in the DOM. A one-shot loadedFolder guard ensures folders build exactly once.

04

createFolders() awaits the four promisesBy now the data has usually already arrived. This overlap is the changelog entry “now folder load faster”.

05

Reconcile two order listsSaved prefs contain folder-* pseudo-entries; the live list contains only containers. Folders are spliced in at index + newOnes.length — the offset compensating for containers Unraid appends at the front.

06

Per folder: move real rows, clone previewsThe live <tr> is moved into hidden folder storage; a clone populates the icon strip. Move preserves Unraid’s handlers; the clone is disposable chrome.

07

Return remBefore; caller rewinds its loop counterThe child splices entries out of the array the parent is iterating. Every absorbed row that sat before the folder shifts the cursor back by one. This works — and it is the most fragile thing in the codebase.

Folders as pseudo-containers

The structural trick worth stealing: a folder is stored in Unraid’s own ordering array as an entry named folder-<id>. Unraid persists drag-and-drop order to userprefs.cfg; because a folder occupies a slot like any container, dragging it among containers just works, and Unraid persists it without knowing folders exist. No parallel ordering system, no sync problem.

The price is one small lie the plugin maintains: Unraid re-numbers on save and gets confused by the extra entries, so a five-line ajaxPrefilter rewrites the outgoing payload with a clean index sequence. That interceptor is the seam of the entire design.

04 — State

Two JSON files and a union

Folders are keyed by a random 20-character ID, never derived from the name — so renaming cannot orphan a folder and two folders may share a name. Cheap and correct. settings is a flat bag of ~19 fields with no schema and no migration step: every consumer defaults each missing field individually, which is crude but has absorbed two years of additions without a single migration. The cost is that the defaults live at every read site instead of being stated once.

Membership is computed from three sources

MechanismEvaluatedWho it actually serves
containers[]PersistedHumans clicking checkboxes in the edit form.
regexClient-side, every renderNaming conventions — ^arr-, or Pterodactyl’s UUID-named eggs. Picks up new containers with no persistence and no staleness.
label folder.view2Client-side, every renderThe important one. A docker-compose.yml declares its own folder membership, so a stack torn down and recreated lands back in the right folder untouched. Neither other mechanism can do this.

Three mechanisms for one concept reads as over-design until you see the third — the compose use case named in the README is unreachable without it.

05 — PHP

One function carries the weight

Seven of nine endpoints are three lines. All real work is in lib.php, and readInfo alone is roughly 55% of the PHP. It assembles the per-container payload the UI needs, and it contains one genuinely good optimisation and one genuinely expensive habit.

Good — templates parsed once

Unraid stores per-container metadata in XML templates. The naive shape is “for each container, find and parse its template” — O(containers × templates) DOM parses. Instead every template is parsed once into a map keyed name|image, then looked up in O(1). A small change with a real win on a forty-container server.

Good — a fallback chain that became the main road

A container either has an Unraid template or it doesn’t — compose, CLI, and Portainer containers don’t. Rather than degrade, the code reads the same fields from net.unraid.docker.* labels, the convention Unraid itself uses. The changelog shows this being learned across several releases. It is now the load-bearing path for compose users, who are the stated audience.

Expensive — Tailscale resolution shells out

Resolving a [hostname] or [noserve] WebUI placeholder means asking the container: up to two docker exec … tailscale calls each, serially, on every list refresh. Injection is guarded correctly — a strict name regex and escapeshellarg — but each exec costs 50–200 ms. Ten such containers is a visible stall. A short-lived cache keyed on container ID is about ten lines.

Duplicated by necessity

readUnraidOrder re-derives the container order exactly as Unraid computes it — prefs lookup, synthetic index for unknowns, array_multisort, natural-sort fallback. Every branch mirrors Unraid’s behaviour, because no reusable function is exported. It will drift; when it does, folders render in the wrong place immediately, which is at least a loud failure.

06 — The best-designed part

Zero-config extensions

The extension system is the only part of the codebase with a designed API rather than an accreted one, and it punches well above the project’s weight. folderEvents is a bare EventTarget — the mechanism is literally one line of source.

Live references, not copies

A listener on docker-folder-context receives the options array before it reaches the menu library and can push its own entries in. A listener on docker-pre-folder-creation can rewrite the folder definition before it renders. No registration API, no manifest, no permission model — mutate the object and the plugin uses your version. Wide open, and exactly right for a tool where the extension author and the operator are the same person.

Filename as routing

mine.docker.js loads on the Docker tab; mine.dashboard-docker.js on both. A regex glob against the filename replaces what would otherwise be a manifest format and the code to parse it. The whole rule fits in one line of the dev guide, and dev/ ships commented templates plus HTML snapshots of the generated markup.

The one gap: styling is CSS-only by policy, because the markup is a single 3,000-character template literal inside createFolder. Extension authors can restyle anything and restructure nothing.

07 — Verified, not speculative

Findings

Everything below was confirmed against the source at a8893f2. Ordered by what would bite a new maintainer first.

Package URL points at a branch that does not exist

Release blocker

The manifest downloads the .txz from …/master/archive/ while the plugin URL on line 8 uses main. The repo’s default branch is main. It also still points at the upstream VladoPortos repo rather than this fork.

folder.view2.plg:290 · vs line 8

Manifest version is behind the archive

Release blocker

The manifest declares 2025.04.13, but archive/ contains builds through 2025.05.26. A fresh install from the manifest gets an older package than the repo holds.

folder.view2.plg:9 · archive/

Unvalidated type reaches a filesystem path

Hardening

$_GET['type'] and $_POST['type'] flow straight into "$configDir/$type.json" with no whitelist, reachable from four endpoints. Behind session auth and not remotely exploitable — but the fix is a two-value in_array check.

server/lib.php:73–105 · read · create · update · delete

Mutating endpoints carry no CSRF token

Hardening

create.php, update.php and delete.php accept requests without Unraid’s csrf_token, and delete.php mutates on a GET. Unraid’s own endpoints require the token; matching that convention is roughly ten lines.

server/create.php · update.php · delete.php

Index arithmetic over a live-mutated array

Structural

createFolders iterates the order array while createFolder splices entries out of it, with a DOM write in between; the child returns a count and the parent rewinds its cursor. The changelog documents at least six bugs traceable to this pattern. A two-pass design — compute the arrangement, then apply it — removes the entire class.

scripts/docker.js:124–126 · and its two siblings

Triplicated lifecycle

Structural

docker.js, dashboard.js and vm.js implement the same lifecycle three times — and dashboard.js does it twice internally, once per type. About 3,800 lines where perhaps 1,400 of distinct behaviour exists. The differences are parameters, not architecture. Every fix must land in three or four places; the ones that get missed are the recurring “small fix for VMs” changelog entries.

scripts/docker.js · dashboard.js · vm.js

Debug logging shipped as production code

Readability

About 290 of docker.js’s 1,752 lines are if (FOLDER_VIEW_DEBUG_MODE) console.log(…), interleaved with logic at roughly one line in six, and dead in every shipped build. A no-op log() helper recovers the readability at no cost.

scripts/docker.js · server/lib.php

Two order lists, swapped names

Trap

read_order.php is read into a variable called unraidOrder; read_unraid_order.php into one called order. The names are inverted relative to the endpoints. Expect to re-derive this every time you open the file.

scripts/docker.js:16–19

Server is the source of truth, git is the backup

Workflow

copy_to_git.sh does rm -Rf src/…/* then copies the live Unraid server back into the repo. It works, but it inverts the normal direction and silently destroys any repo-only change. Prefer editing in the repo and copying out — with no build step, a file copy is the whole deploy.

08 — Assessment

Where it earns its keep

Genuinely good

  • Move, don’t re-render. Inheriting every Unraid row behaviour permanently and for free is worth the fragility it costs.
  • Folders as pseudo-containers. Reusing Unraid’s ordering storage eliminates a whole category of sync bug.
  • Request/render overlap. Fire in the patched loadlist, await in createFolders — free latency, correctly obtained.
  • Three membership mechanisms. Each serves a distinct real user; the label path is what makes the compose story work at all.
  • Template pre-parsing. The one place the code chose an algorithm over the obvious loop.
  • The extension system. Event-based, zero-config, documented, with working templates.
  • The debug keystroke dump. A tool built specifically to make the hardest subsystem inspectable. Most projects this size ship nothing.

Genuinely weak

  • Triplication dominates. ~3,800 lines carrying ~1,400 lines of distinct behaviour, and the drift shows up in the changelog.
  • The remBefore pattern. Correct today, but a bug factory by construction.
  • Debug logging at one line in six. It obscures the code it documents.
  • Two unvalidated-input issues. Neither exploitable, both cheap to close — perhaps twenty lines for the pair.
  • Two broken manifest facts. A fresh install from this repo either fails or installs the wrong build.
  • No tests, no CI, no linter. Understandable given nothing runs off an Unraid box — but the order reconciliation is pure input→output, is where the bugs actually are, and is small enough to cover properly.

If you were redesigning it

Keep the DOM-relocation strategy. It is the correct answer to the constraint and two years have vindicated it. Change three things:

  1. One core, three adaptersA single engine taking a config of selectors, endpoints and intercept strategy. Collapses ~3,800 lines to ~1,400 and makes “small fix for VMs” a phrase that never appears again.
  2. Two-phase renderPhase one: a pure function, (folders, orders, info) → layout plan. Phase two: apply the plan to the DOM. Phase one is unit-testable without a browser, and the remBefore bug class ceases to exist.
  3. A declared settings schemaOne defaults object replacing ~19 fields’ worth of optional-chaining scattered across every read site — and a place to put migrations when you eventually need one.

None of that is required for the plugin to keep working. It is what would make the next two years of Unraid releases cheaper than the last two.
